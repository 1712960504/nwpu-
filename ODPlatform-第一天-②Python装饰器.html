装饰器(decorator)是 Python 里把"附加行为"干净地贴到函数上的机制,也是第一天最该吃透的语言点。看懂它,你就看懂了项目里的计时工具、日志工具,以及 Flask、pytest 等几乎所有框架里那些 @ 开头的写法。

0这一篇要让你搞懂什么

读完这一篇,你应该能做到三件事:

  • 看懂任何一个装饰器——知道 @something 写在函数上面时,Python 到底偷偷做了什么。
  • 自己写一个装饰器——包括"带参数"的那种(三层嵌套),不再觉得它是魔法。
  • 读懂并写出项目里真正的 time_it——理解它每个参数为什么存在,而不是照抄。

我们从最朴素的地方出发,一步一步推到项目代码。中间所有小例子都请你打开 Python 亲手跑一遍——装饰器是"看十遍不如跑一遍"的东西。

1一步步理解装饰器

装饰器不是魔法。把它拆成几步,任何人都能看懂。

1.0 第 0 步:函数是"一等公民"

在 Python 里,函数和整数、字符串一样,可以赋值给变量、当参数传、当返回值。这是装饰器的全部基础——先把这件事坐实。

💡 抓住这一点

f = shout 里 shout 没有括号。shout(无括号)是"函数这个对象本身";shout("hi")(有括号)才是"调用它、拿到结果"。装饰器从头到尾都在玩"把函数当对象传来传去",这个区别务必先盯死。

1.1 第 1 步:闭包——内层函数"记住"外层变量

一个函数里可以再定义一个函数并把它返回。返回的内层函数会"记住"它出生时所在的外层变量。这叫闭包(closure)。

double 和 triple 是同一个 multiply 函数生出来的两个版本,但一个记着 n=2、一个记着 n=3。"函数 + 它记住的外层变量"这一对,就是装饰器能"携带配置"的原理。

1.2 第 2 步:装饰器 = "接收函数、返回增强函数"的函数

把闭包用在"包装另一个函数"上,就是装饰器。下面手写一个计时装饰器(这是教学示例,先不管项目),看清它到底做了什么。

💡 @timer 只是语法糖

@timer 写在 load_image 上面,Python 会自动执行 load_image = timer(load_image)。也就是说,原来的 load_image 被悄悄换成了 wrapper。之后你每次调用 load_image,实际跑的是 wrapper:它先计时、再调真正的原函数、最后打印耗时。业务代码(load_image 函数体)一个字都没改。这就是装饰器的全部威力。

1.3 第 3 步:别忘了 functools.wraps(新手最常漏)

上面的 wrapper 有个隐患:被装饰后,load_image.__name__ 会变成 'wrapper',文档字符串也丢了。这会让日志、调试、自动文档全部错乱(日志里只看到一片 wrapper,根本分不清是谁)。functools.wraps 就是用来把原函数的"身份证"(名字、文档等)复制到 wrapper 上的。

⚠ 两个新手必踩的点

一、@functools.wraps(func) 几乎是写装饰器的"标配第一行",忘了它日志就会乱套。二、这里用 try/finally 而不是顺着写:finally 保证哪怕原函数中途抛异常,计时也照样落下——出了事更要知道它跑了多久。这两个习惯,项目里的 time_it 也都用上了。

2带参数的装饰器(三层嵌套)

真实工具里,我们常想这样用:@timer("数据转换")——给计时打个标签。这就要求装饰器先接收参数,再接收函数,于是多一层嵌套,变成三层。

💡 记忆口诀:几层括号,几层函数

@timer("x") 比 @timer 多了一对括号(传参),所以多包一层。三层各司其职:外层收参数 → 中层收函数 → 内层做事。
看懂这三层,你就看懂了 Flask 的 @app.route("/")、pytest 的 @pytest.mark.parametrize(...) ——所有"带括号的装饰器"都是这个结构。项目里的 time_it 正是三层结构。

3time_it:从真实需求推出设计

概念讲完,该看项目里的真家伙了。它叫 time_it(带下划线,别和上面教学用的 timer 或 Python 标准库的 timeit 搞混),住在 common/performance_utils.py 里。

它的形状不是凭空设计的,是被第一天初始化项目时的真实需求逼出来的。把需求列出来,设计就自己长出来了:

真实需求逼出的设计决策
给"项目初始化"这种一次性流程计时,一行贴上去就好做成装饰器 @time_it(),贴在函数上,函数体不动
有些快函数跑一次看不准,想多跑几次取平均加参数 iterations:循环跑 N 次,报平均(必要时也报总耗时)
耗时可能是几微秒,也可能是几分钟,单位要好读内部 _format_time_auto_unit:自动在 微秒/毫秒/秒/分钟/小时 之间切换
日志里要能看出"这条耗时是哪个模块报的"加参数 logger_instance:让调用方把自己的 logger 传进来
有些场景每次调用名字都不一样(比如逐项质检)name 不仅能传字符串,还能传一个函数,运行时动态算出名字
计时要准、不受改系统时钟影响用 time.perf_counter()(单调高精度),不用 time.time()

4time_it 完整代码 + 逐段导读

下面是项目里 common/performance_utils.py 的完整真实代码——你在 D1 实战里敲的就是这一份,一字不差。先通读一遍,再看下面的逐段导读。

逐段导读(看完上面代码再读这里)

  • logger = logging.getLogger(__name__)(模块顶部)。这是从今天起所有业务模块的标准开头:拿一个以本模块命名的 logger,只负责"发声"。它怎么变成彩色、怎么进文件,是日志工具的事(见第三篇),这里不操心。
  • 三层结构。time_it(...) 收参数 → decorator(func) 收函数 → wrapper(...) 真正执行。和第 2 节的口诀完全对上:几层括号几层函数。
  • log = logger_instance if ... else logger。这是参数里最实用的一个:不传就用本模块 logger;传了就用调用方的。项目里 init_project 就传了自己的 logger,于是日志里显示"这条耗时来自 od_platform.cli.init_project",一眼可读。
  • _resolve_name 为什么套 try/except?当 name 是个函数(运行期算名字)时,万一它自己算崩了,绝不能连累被测函数——所以兜底退回函数名,只打个 warning,测量照常进行。这是"工具不能比业务还脆弱"的体现。
  • iterations 循环。for 里跑 N 次、累加耗时,再求平均。iterations == 1 时只报一次耗时;多次时额外报总耗时。注意计时用 time.perf_counter()——单调、高精度,不会因为系统时间被改而算出负数。
  • @wraps(func)。就是第 3 步讲的"保住原函数身份证",让日志里 %(funcName)s 显示真名而不是 wrapper。
🏢 对照一下:你学的概念,全用上了

闭包(wrapper 记住外层的 iterations/name/log)、三层嵌套(带参数)、functools.wraps、try/except 兜底、perf_counter 计时——第 1、2 节铺垫的每一块,在这份真实代码里都能找到落点。这就是"概念"变成"产品代码"的样子。

6工程判断:为什么用装饰器做这件事

🧭 横切关注点,要"贴"上去,不要"抄"进去

计时是典型的横切关注点:它和"这个函数在算什么"毫无关系,但到处都要。装饰器让你把它"贴"上去,而不是把 t0=...; t1=... 抄进每个函数体里污染逻辑。把非功能性关注点(计时、日志、重试、缓存)从功能代码里剥离,是这门课最值钱的工程判断之一。下一篇的日志工具,走的是同一种思想。

7留个悬念:如果让你把它扩成"推理级"性能工具 🚀

今天这个 time_it 解决的是"给一个流程测一次耗时"。但等你后面写到推理那一块,需求会变得更刁钻。下面这些问题,我们今天故意不解决——留给你先想,留给推理课去答。能想清"该往这个装饰器上加什么",你对装饰器的理解就从"会用"升到了"会设计"。

🤔 留给你的几个开放问题

① 我想测的不是"整个函数",而是"函数里的一小段"怎么办?
装饰器只能包整个函数。要测一段代码,得换个工具。(方向:上下文管理器 with Timer("preprocess"): ...——Python 里和装饰器并列的另一种"包裹"机制。)

② 推理一帧的耗时没意义,我要"1000 帧里平均/最差/p95 是多少"。
time_it 每次调用各打各的,不会跨调用累加。(方向:做一个统计累加器,把每次耗时按标签收集起来,最后算 avg/min/max/p95 再统一报告。)

③ 推理是多线程的,多个线程同时记耗时会不会打架?
会。多个线程同时往一个列表里写,可能丢数据或报错。(方向:线程锁 threading.Lock 保护那一下写入。)

④ 生产环境上线后,我不想让计时拖慢系统,能一键关掉吗?
现在它总是会计时。(方向:一个全局开关,关闭时让装饰器退化成"直接调原函数",近零开销。)

⑤ 我想看推理循环的实时帧率(FPS)。
这是另一种统计口径。(方向:一个滑动窗口,记住最近 N 帧的时间戳,用帧数除以时间跨度。)

这些都不是今天要写的——它们是"性能工具"这条线后面会长出来的枝。今天你先把一个装饰器怎么从需求推出设计、怎么逐行写对吃透,就够了。

8小结

  • 装饰器不是魔法。它建立在"函数是一等公民 + 闭包"之上,本质是"接收一个函数、返回一个增强函数",@ 只是 f = deco(f) 的语法糖。
  • 三层口诀:几层括号几层函数。带参数的装饰器 = 外层收参数 → 中层收函数 → 内层做事。项目里的 time_it 就是这个结构。
  • 两个标配习惯:@functools.wraps(func) 保住原函数身份证;perf_counter 做高精度单调计时。
  • 设计是被需求逼出来的。time_it 的每个参数(iterations/name/logger_instance)都对应一条真实需求,不是为了花哨。
  • 横切关注点要剥离。计时"贴"上去、别抄进函数体——这是贯穿整个 common 层的思想。
