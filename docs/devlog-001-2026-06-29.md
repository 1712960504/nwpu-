## 1. 本日开发目标

### 1.1 总体目标

完成 ODPlatform 项目的**零日启动**与**第一天基础设施搭建**。具体包括：

1. **仓库初始化**：Git 仓库创建、`.gitignore` 配置、workspace marker 文件部署
2. **Monorepo 目录树落地**：按照 ADR-001 决策，创建 `apps/platform/` + `apps/desktop/` + `apps/web-backend/` 三端骨架
3. **Python 包结构建立**：`od_platform` 命名空间包，含 `common/`、`cli/`、`test/` 三个子包
4. **通用基础设施层 (common/) 完整实现**：6 个核心模块
5. **CLI 入口开发**：`odp-init` 命令——项目自动初始化
6. **构建系统配置**：双层 `pyproject.toml`（仓库根 + app 端）
7. **开发工具链集成**：ruff、mypy、pytest 配置

### 1.2 设计原则

| 原则 | 说明 |
|---|---|
| **marker-file 模式** | 通过 `.odp-workspace` 文件定位仓库根目录，避免硬编码路径 |
| **冒泡日志架构** | 根 logger `"od_platform"` 挂 handler，业务模块 `getLogger(__name__)` 通过 logger 树自动继承 |
| **先建 common，再建 CLI** | 通用工具不依赖任何业务逻辑；CLI 是 common 的第一个消费者 |
| **幂等设计** | 日志配置、目录创建等操作均支持重复调用而不产生副作用 |
| **软依赖策略** | torch、psutil、ultralytics 等重型库作为可选依赖，缺失时优雅降级 |

#### 2.3.1 `paths.py` — 路径常量集中管理

| 属性 | 说明 |
|---|---|
| **文件路径** | `apps/platform/src/od_platform/common/paths.py` |
| **代码行数** | 170 行 |
| **核心职责** | 集中定义所有项目路径常量，作为路径的**唯一数据源 (Single Source of Truth)** |

**设计要点：**

1. **Marker-file 定位算法**：`_find_workspace_root()` 从当前文件位置向上遍历父目录，查找 `.odp-workspace` 标记文件。此模式参考了 pytest (`pytest.ini`)、poetry (`pyproject.toml`)、git (`.git`) 和 npm (`package.json`) 的行业标准做法。

2. **路径分层**：
   - **共享资产** (`ROOT_DIR` 下)：`DATA_DIR`、`MODELS_DIR`、`RUNS_DIR`——所有端可访问
   - **端私有资产** (`APP_DIR` 下)：`CONFIGS_DIR`、`LOGGING_DIR`、`UNIT_TEST_DIR`——仅 platform 端

3. **`get_dirs_to_initialize()`**：返回需初始化的全部 20 个目录列表，作为 `init_project.py` 的**唯一数据源**——paths.py 决定"要哪些目录"，init_project 只负责"创建"。

```python
# 关键常量列表
ROOT_DIR                # workspace 根 (通过 marker file 解析)
APP_DIR                 # apps/platform (platform 端根目录)
DATA_DIR                # data/
RAW_DATA_DIR            # data/raw/ (只读原始数据)
PROCESSED_DATA_DIR      # data/processed/ (派生数据，可再生)
PRETRAINED_MODELS_DIR   # models/pretrained/ (输入)
TRAINED_MODELS_DIR      # models/trained/ (产物)
CHECKPOINTS_DIR         # models/checkpoints/ (恢复训练)
CONFIGS_DIR             # apps/platform/configs/
LOGGING_DIR             # apps/platform/logging/
DOCS_DIR                # docs/
SCRIPTS_DIR             # scripts/
```

#### 2.3.2 `logging_utils.py` — 企业级日志系统

| 属性 | 说明 |
|---|---|
| **文件路径** | `apps/platform/src/od_platform/common/logging_utils.py` |
| **代码行数** | 170 行 |
| **核心职责** | 配置项目根 logger，提供彩色控制台 + 带时间戳文件双输出 |

**架构设计（冒泡模型）：**

```
进程启动
  │
  ├── CLI 入口调用 get_logger()  ← 装配 handler 到 "od_platform" (根 logger)
  │     ├── console handler (ColoredFormatter, 彩色)
  │     └── file handler (FileHandler, 完整格式)
  │
  └── 业务模块写 logger = logging.getLogger(__name__)
        │  __name__ = "od_platform.common.paths"
        │  __name__ = "od_platform.cli.init_project"
        │  __name__ = "od_platform.common.system_utils"
        └── 这些 logger 通过 logger 树向上冒泡到 "od_platform"
              → 自动使用已装配的 handler → 无需每个文件配置日志！
```

**日志文件命名规范：** `<prefix>_<YYYYmmdd-HHMMSS-ffffff>[_<model_name>].log`

**日志格式：**

| 输出目标 | 格式 |
|---|---|
| **文件** | `%(asctime)s - %(name)s - %(levelname)-8s - %(filename)s:%(lineno)d - %(funcName)s - %(message)s` |
| **控制台** | 彩色格式：时间 · [级别] · 文件名:行号 · \| 消息内容 |

**彩色方案：**

| 级别 | 颜色 |
|---|---|
| DEBUG | 白色 |
| INFO | 绿色 |
| WARNING | 黄色 |
| ERROR | 红色 |
| CRITICAL | 粗体红 + 白底 |

**幂等保护：** `get_logger()` 首次调用装配 handler，后续调用通过 `if logger.handlers: return logger` 直接返回，避免重复挂载导致日志重复输出。这意味着**整个进程只配置一次日志**。

#### 2.3.3 `decorators.py` — 通用装饰器集合

| 属性 | 说明 |
|---|---|
| **文件路径** | `apps/platform/src/od_platform/common/decorators.py` |
| **代码行数** | 320 行 |
| **核心职责** | 提供 5 个可复用装饰器，覆盖计时、重试、日志、鉴权、校验场景 |

| # | 装饰器 | 签名 | 功能 |
|---|---|---|---|
| 1 | `@timing` | `(func?, log_level, msg)` | 记录函数执行耗时（`time.perf_counter()` 高精度计时），支持 `@timing` 和 `@timing()` 两种语法 |
| 2 | `@retry` | `(func?, max_attempts, delay, backoff, exceptions)` | 失败自动重试，指数退避延迟 (`delay *= backoff`)，可指定捕获异常类型 |
| 3 | `@log_call` | `(func?, log_level, log_args, log_result, max_arg_len)` | 记录函数调用入口参数和出口返回值，支持参数截断保护 |
| 4 | `@require_permission` | `(permission: str \| Callable)` | 权限检查，支持字符串注册表查询或自定义 lambda 检查函数 |
| 5 | `@validate_params` | `(validator: Callable, error_msg)` | 参数预校验，校验失败抛出 `ValueError` |

**设计亮点：**

- **双语法支持**：`timing`、`retry`、`log_call` 均支持无参 (`@timing`) 和有参 (`@timing(log_level=DEBUG)`) 两种写法，通过 `func is not None` 判断分发
- **辅助函数 `_truncate_repr()`**：截断过长对象，防止日志/异常信息泛滥
- **自测代码**：每个装饰器的 `__main__` 自测段覆盖正常路径和异常路径

| **决定 2** | `.odp-workspace` marker file 定位根目录 | `paths.py::_find_workspace_root()` |

| **决定 4** | 共享资产 vs 端私有资产分离 | `paths.py` 中 `ROOT_DIR` vs `APP_DIR` 路径分层 |
| **决定 5** | 原始(只读)与派生(可再生)数据分离 | `data/raw/` vs `data/processed/` |
| **决定 6** | 数据目录 gitignore 但保留 README | `.gitignore` 白名单策略 |
| **决定 7** | 双层 pyproject.toml（根工具 + 端构建） | 根 `pyproject.toml` + `apps/platform/pyproject.toml` |

### 3.2 Day 1 新增设计决定

| 编号 | 决定 | 理由 |
|---|---|---|
| **D1-1** | 日志采用冒泡模型（根 logger + 业务 `getLogger(__name__)`） | 业务模块零配置，CLI 入口一次装配，全进程共享 |
| **D1-2** | 日志配置幂等保护 | 防止重复挂载 handler 导致日志输出 N 遍 |
| **D1-3** | `get_dirs_to_initialize()` 作为目录列表唯一数据源 | paths.py 决定"要什么"，init_project.py 只负责"创建"，职责分离 |
| **D1-4** | 软依赖策略（psutil/torch/ultralytics 可选） | 环境快照是辅助功能，不阻止平台核心功能启动 |
| **D1-5** | 装饰器支持双语法（`@timing` / `@timing()`） | 用户体验一致，符合 Python 社区惯例 |
| **D1-6** | CJK 字符宽度感知（宽字符 = 2） | 终端中文对齐刚需，覆盖 7 个 Unicode 范围 |
