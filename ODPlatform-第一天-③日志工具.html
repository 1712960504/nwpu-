日志工具 与 企业级日志实践

地基里第二个要造的工具是日志。这块"特别难"的不是 API,而是判断力:什么时候记、记到什么级别、记去哪、怎么不重复、怎么不拖慢系统。这一篇把判断力和项目里真正的 logging_utils.py 一起讲透。

日志 API 很简单,十分钟能学会。但日志是产品的一部分——它要在半夜出故障、你不在现场时,替你还原"当时到底发生了什么"。所以真正难的不是 API,是那几条"什么该记、记到哪"的判断。这一篇先把判断力立起来,再落到项目代码。

0为什么日志难的不是 API,是判断力

上一篇我们造了 time_it,它最后一行是 log.info("性能报告: ...")——计时报告得有个地方"打出来"。这个"地方",绝不该是裸 print。本篇就来造那个统一的日志工具,并搞清它背后的设计。读完你会明白:为什么所有业务模块顶部都写 logger = logging.getLogger(__name__),以及这行字背后藏着的一整套约定。

⚠ 一句话

print 是"给自己看一眼就删"的;日志是产品的一部分。一个用 print 调试的项目,等于在故障现场什么证据都没留。

2logging 的四个核心概念

标准库 logging 把日志拆成四个角色,理解它们,就理解了所有日志框架:

  • Logger(记录器):你代码里调用的入口(logger.info(...))。它有层级——用 getLogger(__name__) 会得到像 od_platform.cli.init_project 这样的树状名字。
  • Handler(处理器):决定日志去哪——控制台(StreamHandler)、文件(FileHandler)……一个 Logger 可挂多个 Handler。
  • Formatter(格式器):决定每条长什么样(时间、级别、模块、行号、消息)。
  • Level(级别):DEBUG < INFO < WARNING < ERROR < CRITICAL。Logger 和 Handler 各有一道级别闸门,低于阈值的直接被丢弃。

3企业里日志到底怎么用

① 级别要有纪律(最重要)

级别什么时候用本平台里的例子
DEBUG开发排查用的细节,生产默认不输出到控制台每张图的尺寸、每个框的坐标
INFO关键流程节点,"系统正常地走到了这一步""成功创建目录 data/raw""训练 epoch 12/100"
WARNING不正常但能继续,值得关注"原始数据集根目录为空,请放入数据集"
ERROR某个功能失败了,但程序还能活"创建目录失败,本次初始化中止"
CRITICAL系统级、要立刻有人处理"找不到 workspace 标记,路径系统失效"

② 文件怎么管理:两种常见策略

日志总要落到文件里。什么时候切一个新文件,有两种主流做法,适用场景不同:

策略怎么切适合谁

③ 其余几条铁律

  • 配置只做一次(SSoT)。日志的格式/去向/级别在一处集中配置,绝不各模块各配各的——否则同一条日志会被打好几遍(见第 7 节)。
  • 绝不记敏感信息。密码、token、密钥永远不进日志。
  • 热路径别狂打。推理每帧都打 INFO 会拖垮性能;用 DEBUG,且让格式延迟求值(logger.debug("box=%s", box) 而不是 f-string 拼大对象)。
  • 异常用 logger.exception() 或 exc_info=True。它会自动把完整 traceback 一起记下来(项目里 time_it 的兜底 warning 就用了 exc_info=True)。

4ODPlatform 的日志设计:业务"发声",基础设施"配音响"

把上面那些实践固化成代码,ODPlatform 用了一个特别清爽的设计。它的精髓是一句分工:

💡 金句

"业务模块要做的事是【发声】,不是【配置音响】。把'怎么配 handler'留给基础设施,业务模块只关心'我要说什么'。"

这句话拆成三个角色,正好对应三种代码:

  • 业务模块(paths / system_utils / init_project / 未来的 train…):顶部只写一行 logger = logging.getLogger(__name__),然后 logger.info("...") 发声。它不配 handler,也不知道 handler 长什么样。
  • 基础设施模块(logging_utils.py):提供一个 get_logger() 函数,把 console + file 两个 handler 挂到根 logger "od_platform" 上。
  • CLI 入口(init_project 函数最开头):调用一次 get_logger() 把 handler 装好——之后整个进程里所有 getLogger(__name__) 拿到的子 logger,都会通过冒泡机制走到根 logger,由它的 handler 统一处理。

这里有两个关键机制要讲清:

(1) getLogger(__name__) 形成一棵 logger 树。__name__ 在每个模块里会自动展开成该模块的点号全路径,例如 od_platform.cli.init_project。这些名字天然构成一棵以 od_platform 为根的树。

(2) 冒泡机制(propagate)。一条日志从子 logger 一路冒泡到祖先 logger,任何一层挂了 handler,就会被那个 handler 处理。所以我们只要在根 "od_platform" 上挂一次 handler,全树的日志都能被它接住——这就是"业务模块不必各配各的"的原理。

🏢 这样设计换来什么

零配置:业务模块顶部一行就够,不用关心 handler。来源清晰:日志格式里的 %(name)s 会自动显示是哪个模块打的。可按子树调级别:将来想 debug 某个子系统又不想刷屏别的,一行 getLogger("od_platform.xxx").setLevel(DEBUG) 即可。是 Python 圈的惯用法:任何成熟项目读起来都是这个味道,新人零障碍。

下面是 common/logging_utils.py 的完整真实代码——D1 实战里你敲的就是这一份。先通读,再看导读。

逐段导读(看完上面代码再读这里)

  • 配的是命名 logger "od_platform",不是 Python 的真 root。getLogger("od_platform") 拿到的是那棵树的根。我们把 handler 挂在它身上,并设 propagate=False 让它别再往 Python 默认 root 冒泡(否则会和 Python 自带的 root 重复输出)。
  • 幂等保护 if logger.handlers: return logger。这是头号坑的防护(详见第 7 节):getLogger 对同一个名字永远返回同一个对象,如果不检查就每次都 addHandler,handler 越加越多、同一条日志被打好几遍。这里发现"已经挂过了"就直接返回。
  • 每次运行一个带时间戳的新文件。文件名 <prefix>_<时间戳>[_<模型名>].log,落在 base_path/log_type/ 下。这就是第 3 节说的"按运行切分"——想回看哪一次跑,按文件名一找就到。
  • 两个 Handler,各管一头。文件 Handler 用详细格式(时间-模块名-级别-文件:行号-函数名-消息),排查时信息越全越好;控制台 Handler 用 colorlog 的 彩色紧凑格式,给人看、别太吵。注意文件里不上色(否则是一堆乱码转义符)。
  • %(name)s 字段是点睛之笔。因为业务模块都用 getLogger(__name__),这个字段会自动显示"这条日志来自哪个模块",排查接力链上的 bug 时极其有用。
  • 自测的两步,就是整套设计的缩影。第一步 get_logger() 装 handler(只有 CLI 入口做),第二步 getLogger(__name__) 发声(所有业务代码都这么写)。

7新手头号坑:日志重复打印

⚠ 一条日志被打了 3 遍?八成是这两个原因

原因一:重复挂 handler。如果每次都往 logger 上 addHandler,handler 会越加越多,同一条日志被打印 N 遍。本实现用 if logger.handlers: return logger 守住"只配一次"——这就是第 5 节那行幂等保护的意义。
原因二:子 logger 也挂了 handler 又没关 propagate。日志会冒泡到根再被打一遍。记住我们的纪律:handler 只挂在根 "od_platform" 上,子 logger 只负责发声。根上则设 propagate=False,不再往 Python 默认 root 冒泡。

8留个悬念:如果让你把它做成"生产级" 🚀

今天这套日志,够你在本地翻、亲眼看到每一步发生了什么。但真上了生产,还有一圈活在等着。下面这些问题,我们今天故意不解决——留给你先想,留给后面的专题去答。

🤔 留给你的几个开放问题

① 7×24 的在线服务,日志会不会撑爆磁盘?
"按运行切分"靠的是有"一次运行"边界;长跑服务没有。(方向:第 3 节提过的按大小滚动 RotatingFileHandler——写满就滚、只留最近几份。)

② 错误日志淹没在海量 INFO 里,想单独审计怎么办?
(方向:再挂一个只收 ERROR+ 的 handler,把错误单独导一份 error 日志,专供追责/监控。)

③ 日志要被 ELK / Loki / Datadog 这类平台采集、检索、告警。
纯文本不好机器解析。(方向:结构化日志——每条打成一行 JSON,字段化,平台就能按字段查、按阈值告警。)

④ 配置散在代码里,想集中外置成一份配置文件。
(方向:用 logging.config.dictConfig 把整套配置写成一份字典,甚至外置成 YAML。)

🏢 而且,这里藏着一个反转

更值得想的是:真到了生产,日志可能根本不该往项目目录里写文件。现代云原生服务遵循 "12-factor" 原则——把日志直接打到标准输出(stdout/stderr),由平台(容器、日志采集器)统一收走,不在项目树里留文件。
换句话说,我们今天精心设计的"文件日志",搬到生产是要被换掉的——它在这里,纯粹是为了让你在本地直接翻、亲眼看见过程。这不是说今天白学了:文件日志是理解整套机制的最好骨架;只是你要心里有数,它的"适用边界"到哪为止。

9小结

  • 日志是产品的一部分。不是 print 那种"看一眼就删"的东西——它在你不在场时替你还原现场。
  • 四个角色:Logger(发声入口、有层级)、Handler(去哪)、Formatter(长什么样)、Level(级别闸门)。理解它们就理解了所有日志框架。
  • 核心设计:业务发声,基础设施配音响。业务模块只 getLogger(__name__);handler 由 get_logger() 挂在根 "od_platform" 上;CLI 入口装一次;日志靠冒泡汇拢。
  • 两个必记的防坑点:幂等(if logger.handlers)防重复打印;propagate=False 防二次冒泡。
  • 文件按运行切分(每次跑一个带时间戳的新文件)——适合训练/CLI;长跑服务才用按大小滚动。
🧭 三篇收个尾

第一天没写一行检测代码,但你已经把后面所有模块都要踩的地基打牢了:仓库怎么组织(篇一)、横切关注点怎么用装饰器剥离(篇二)、日志怎么统一(篇三)。这三样的共同思想是同一句——把"和业务无关但到处都要"的事,收口成 common 层一处定义、全局复用的工具。明天开始写数据流水线时,你会发现自己已经在反复用今天造的 get_logger 和 @time_it。好的基础设施,就是让你之后"想都不用想"就能用对的东西。
