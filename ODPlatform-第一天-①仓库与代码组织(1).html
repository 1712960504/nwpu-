读这份文档时请带着一个问题:同样一份代码,为什么有的团队能持续迭代十年,有的三个月就改不动了? 答案往往不在算法里,而在第一天就定下来的这些"地基"决策里。

0为什么第一天先搭地基

后面几个模块(数据、训练、评估、推理、应用)都会反复用到三样东西:知道文件在哪(路径)、知道发生了什么(日志)、知道快慢在哪(性能计时)。如果这些没有统一、可靠的实现,每个人就会各写各的——路径硬编码、用 print 调试、计时代码散落一地。等到集成时,这些"小事"会变成最难拆的雷。

所以第一天的任务,是把这些横切关注点(cross-cutting concern)——和具体业务无关、却到处都要的东西——收口成 common/ 层的趁手工具。但在写第一行 common/ 代码之前,得先想明白一件更大的事:这些代码,放进一个什么样的仓库、什么样的目录结构里? 这就是本篇要回答的。

💡 这一篇和后两篇的关系

本篇讲全局结构(代码放哪、谁依赖谁);第二篇讲 performance_utils.py(用装饰器实现);第三篇讲日志工具。后两篇造的工具,都住在本篇定下的 common/ 这一层里。

🧭 工程判断 · 第一天就要建立的认知

你可以在一个 Monorepo 里把代码写成一团乱麻(目录整齐但到处互相依赖),也可以在 Multi-repo 里保持架构清晰。仓库形式和架构质量是两条正交的轴。本课程后面反复强调的"依赖单向、不许成环",约束的是架构,跟我们用一个还是多个仓库无关。

2Monorepo vs Multi-repo

这是"项目组织形式"层面的核心选择:把整个系统的代码放进一个仓库(Monorepo),还是按组件/服务拆成多个仓库(Multi-repo)。

维度Monorepo(一个仓库)Multi-repo(多个仓库)
跨模块改动原子提交:一次 commit 同时改 common 和调用方,要么全成功要么全回滚要分别提 PR、分别发版、按顺序升级,容易半成品状态
共享代码直接 import,零成本要打包成库、发版、各方升级版本
CI / 工具链一套配置统管;难点是"只测改动到的部分"每个仓库独立,但要维护 N 套
重构跨模块改名/挪动,IDE 一把梭跨仓库重构极痛苦
权限 / 部署权限粒度粗;通常整体或按目录部署owner 清晰、可独立部署
典型采用者Google、Meta、字节等大量内部系统大量微服务团队、开源生态

3ODPlatform 为什么选 Monorepo

本项目是单团队、模块紧耦合的教学/产品级系统,Monorepo 几乎是唯一合理选择:

  • common 被所有人依赖。改一次 common 的接口,需要立刻看到它对数据/训练/推理/应用的全部影响。Monorepo 让这件事在一次提交 + 一次 CI 里完成验证——不会出现"common 升级了但某个模块忘了跟"的半成品状态。
  • 单一真相来源(SSoT)。路径、配置规范、日志规范只在一处定义,全仓库引用,杜绝漂移。这正是后两篇要造的 paths / 日志工具存在的前提。
  • 未来加端,零摩擦。今天只有训练+推理一个端;哪天想加个网页 demo、桌面壳,Monorepo 让新端直接复用 common,而不必把它打包发版给另一个仓库。
💡 但"一个仓库"绝不等于"松散架构"

仓库是 Mono,不代表谁都能随便 import 谁。我们用纪律(将来由 CI 强制)守住"依赖单向、不许成环"。仓库形式解决"代码放哪",架构纪律解决"谁能依赖谁"——两者一起上,才有既好协作、又改得动的系统。这条纪律具体长什么样,见第 5 节。

4ODPlatform 的真实目录树

上面三张图为了把"一个仓库装下所有"讲清楚,把目录画得很简(common/ data/ training/... 平铺在根上)。但 ODPlatform 真正的树,比那个多两层讲究——而这两层,正是被"代码要能被正确 import"和"多端要共享资产"两件事逼出来的。先看全貌:

这棵树有三类东西,用三种颜色就能讲清它的组织逻辑:

三层各自的道理,一句话各说清:

  • apps/ 这一层(端的家)。把"可独立交付的端"归在一起。今天只有 platform 一个孩子,看着多余;但等 web-backend、desktop 到来,它们只是 apps/ 下新增的同级目录,引擎一行代码都不用动。这不是过度设计——我们没为不存在的需求多写一行功能代码,只是把"东西放哪"提前想对了,成本是多敲一个文件夹名。
  • src/ 这一层(一道闸)。把源码塞进 src/,意味着你想 import od_platform 就必须先把它装成包(pip install -e);否则 Python 会"碰巧"import 到那份没装的源码,造成"本地能跑、一上 CI 就崩"的经典坑。src/ 不是繁琐,是强制本地与线上行为对齐的闸门。
  • 共享上提、私有下沉。data/models/runs 是所有端都要用同一份的东西(数据集动辄上 GB,复制多份既浪费又会不同步)→ 提到顶层。logging/configs/tests 是某个端自己的东西 → 留在端内部,谁的归谁。
🏢 一个容易混的命名点

包名 od_platform 用下划线——因为它要被 import,而 import od-platform 会被当成"od 减 platform",是语法错误。对外的安装名则是连字符的 od-platform(即 pip install od-platform)。两个名字指同一个东西,只是分属"导入层"和"安装层",各遵各的规矩。

这棵树完整的"为什么每一行都长这样",是设计课(D0)一个问题一个问题推出来的;本篇只需你记住结果与三层逻辑,后两篇造工具时会反复踩在它上面。

5依赖纪律:单向、无环(不是"只能向下")

目录解决"东西放哪",还剩最隐蔽、最要命的一个问题:谁能依赖谁?

项目做大一点,你会有好几个业务模块:数据处理、训练、评估、推理。写着写着它们开始互相 import:推理为图省事直接 from training import ... 借个函数,评估又反过来用了推理里的东西……一开始都能跑。然后某天你改了训练里一个函数签名——推理报错;你去修推理——评估又报错。模块之间织成一张网,碰任何一根线整张网都跟着抖。这种项目的特征是:"能跑",但"不能动"。

⚠ 一个常见的讲法误区

很多教程会说"依赖只能向下、严格分层"。这话不够准。真实里"评估"本就要调用"推理"去跑出预测,这是一条正当依赖,禁掉它你只能把推理硬塞进 common(撑胖底座)或重复实现一遍。所以要守的纪律不是"互不依赖",而是更准的一条——

依赖只能单向流动,不许成环(acyclic)。评估依赖推理可以,只要推理不反过来依赖评估;你要禁的是环,不是所有平级的边。把"无环"守住,那张网就被拆成一棵有向无环的树:动一根枝子,不会牵动那些不依赖它的枝子。

🧭 工程判断 · 为什么这条纪律在今天格外重要

你会非常频繁地改动这个项目——加功能、重构、替换实现,很多时候还交给 AI 去做。一个无法被安全改动的项目,在代码近乎免费的时代是一种负资产:你越想快速迭代,它崩得越频繁。把"无环"守住,就是让"改一处不波及无关的地方"成为可能。这条线画不进目录里,只能靠每段代码的评审守住。

6留个悬念:这套结构将来会怎么长 🚀

到这里,你已经拿到了一套"够用且讲得通"的仓库结构。但教学不能一次把所有牌摊给你——下面这几个问题,我们今天故意不解决,留给你先想、留给后面的课去答。能把它们想清楚,你对"结构"的理解就从"会用"升到了"会判断"。

🤔 留给你的几个开放问题

① Monorepo 到什么规模该拆成 Multi-repo?
我们这个阶段选 Monorepo,但它不是万能的。仓库到几百万行、团队到上百人、各端发布周期严重打架时,Monorepo 的代价(CI 变慢、权限太粗)会盖过它的好处。那个临界点在哪、用什么信号判断该拆了?

② 多端真上线,"共享"的还共享得了吗?
今天 platform 和未来的 web-backend 共享顶层 data/、models/,靠的是"同一台机器上的文件路径"。可真实企业里,对外推理的后端几乎一定在另一台机器/容器/集群上,它拿不到你训练机本地的 models/trained/best.pt。那它怎么拿到训练产物?(提示方向:Monorepo 解决的是代码复用,产物分发是另一层——对象存储 / 模型仓库 / 数据版本化。)

③ "依赖不许成环"这条纪律,靠人盯得住吗?
评审能抓一时,但人会累、会漏。怎么让"成环"在它被引入的那一刻就被自动拦下来?(提示方向:把这条规则交给 CI 流水线去强制,让一次违规的提交直接红掉。)

这三个问题都没有标准答案要你现在背;它们是路标,告诉你"今天学的这套,边界在哪、下一站往哪走"。

7小结

这一篇没写一行检测代码,但你已经拿到几条能用一辈子的判断:

  • 三个层面别混。仓库数量(项目组织)、目录结构(代码组织)、依赖关系(架构)是三件事;目录树不是架构,依赖关系才是。
  • 仓库形式 ⊥ 架构质量。Monorepo 让单团队协作和 SSoT 最省力,但架构纪律要靠评审/CI 单独守,跟用几个仓库无关。
  • 结构是被逼出来的,不是套模板。apps/ 是为"未来的端"留的家,src/ 是强制"装了才能 import"的闸,共享上提/私有下沉是按"被谁共享"分层——每一层都有它要解决的具体问题。
  • 依赖单向、无环。不是"只能向下、严格分层";平级模块允许互相依赖,禁的是环。common 在最底、被所有人依赖,所以第一天先造它。
